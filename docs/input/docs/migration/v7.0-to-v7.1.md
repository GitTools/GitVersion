Description: Migration guidance for upgrading from GitVersion v7.0 to GitVersion v7.1.

This guide covers the changes from GitVersion v7.0 to v7.1. If you are upgrading
from v6, first follow the [v6 to v7 guide](/docs/migration/v6-to-v7).

## Managed Git backend

LibGit2Sharp and its native binaries are removed in v7.1. The managed backend
introduced as the v7.0 default is the sole backend. Unset
`GITVERSION_GIT_BACKEND=libgit2`; selecting `libgit2` now fails with migration
guidance. Explicit `managed` remains accepted throughout v7.x; the selector is
removed in v8.

Keep the `git` executable on `PATH` for clone, fetch, checkout and build-agent
repository normalization. Version calculation on an already-prepared checkout
does not require Git CLI network or write operations.

## Native CLI distribution

Standalone CLI archives and RID-specific `GitVersion.Tool` packages are compiled
with NativeAOT by default. Standalone executables do not require a shared .NET
runtime; .NET tool installation and command discovery still require a supported
.NET SDK. Native executables retain their operating system's native dependencies.

The top-level tool package dispatches to the matching native RID package. Pin
the tool version used by your team and CI, then compare version calculation and
consumed outputs on representative tagged, feature and release commits.

Libraries and `GitVersion.MsBuild` remain managed assemblies. The MSBuild package
retains its matching managed CLI dependencies; it does not load a native tool
executable as a task assembly. Test hosts and development builds also remain
managed. AOT, trimming and single-file compatibility diagnostics are build
errors for the shipped CLI projects.

## Building from source

Native publication must run on a compatible host. Windows and macOS packaging
uses the corresponding host. Linux packaging uses the repository's glibc/musl
Docker build stages on the selected CPU architecture, then collects all seven
RID-specific tool packages.

After preparing the build with `./build.ps1 -Stage build -Target BuildPrepare`,
Linux and macOS contributors with Docker can run the same Linux packaging
targets as CI:

```shell
dotnet run/build.dll --target=PackageLinux --native_container=glibc
dotnet run/build.dll --target=PackageLinux --native_container=musl
```

Each command builds the matching image and runs packaging as the non-root
checkout owner. Native packages are written under `artifacts/packages`.

After collecting the NuGet packages and Linux archives from every required host
under `artifacts/packages`, validate the complete set with the same Cake target
used by CI:

```shell
dotnet run/build.dll --target=PackageValidateCollected
```
